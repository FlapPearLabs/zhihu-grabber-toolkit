## §1 任务背景与动机

`zhihu-grabber-toolkit` 的 V2 rich-content-fidelity 已实现并合并了 Phase 1–4（Rich Content / Question metadata / Comments），并确立了严格的三层内容模型与 Agent 安全隔离合同。当前待推进的边界（V2 §25 Open questions、Phase 5 Agent projection / Capability Isolation）与若干产品层面的清晰度缺口，构成 V0.3 的动机：

1. **搜索规模不可见**：`search` 命令当前只返回问题 ID / 标题 / 类型（见 §12.1），用户在选择抓取目标时不知道该问题有多少回答，无法预估语料规模与成本。
2. **视频能力的产品立场缺失**：V2 §16 将视频定位为「detect + metadata，待真实样本」，但从未给出一个明确的、可被实现遵循的**永久性产品立场**。本 Spec 将其收敛为「永久不支持」（纯产品/文档决策，无新 CODE，见决策 B / R4）。
3. **Agent projection 与能力隔离的当前阶段归属**：V2 §9/§9.1/§9.2 已定义 Agent 投影与能力隔离合同，Phase 5B 已收口；V2 §9.2.9 规定下一步是 **Phase 5C — Capability Isolation Feasibility Check**。用户明确 V0.3 **当前就推进** Agent projection + capability isolation，因此 Phase 5C 可行性检查**由 V0.3 在当前阶段真实执行**（见决策 C / R2），而非「只消费既有结论」。
4. **countMismatch 的语义污染**：当前 `verifier.js` 把 `countMismatch` 同时写入 `warnings[]`（§12.4），使其被当作「失败/警告」信号，但实际语义只是诊断性提示（V2 §20 与 references/verification.md 明确「仅提示，不设失败门」）。需要把该事实从 `warnings[]` 中剥离（决策 D）。
5. **大型语料的 token / 成本压力**：corpus-anthology 已有 `popular-sample`（高赞样本）与 `digest`（100% 覆盖）。但介于「仅看高赞」与「全量摘要」之间的**按覆盖率降序取前 X% 用完整正文**这一常见产品形态缺失；且全量 digest 在超大语料下的成本需要中间聚合层降本，同时**不得削弱既有 coverage / evidence gate**（含 evidence lineage 不变量，见 §7.3 / R10）。

## §3 决策 A：搜索结果返回回答数量

**标识：** `SEARCH_ANSWER_COUNT_DISCOVERY_REQUIRED = YES`

### §3.1 当前仓库事实与上游 schema 状态

**CURRENT_REPOSITORY_FACT（已核对 master `e67d3ca`，可断言）：**
- 官方搜索客户端 `zhihu-answer-grabber/src/official.js` 的 `searchQuestions()` 返回 `parsed.Data?.Items`；当前代码 `extractQuestionId(item)` 仅消费 `item.Url`。
- `zhihu-answer-grabber/src/cli.js` 的 `cmdSearch()`（lines 221–256）将 Item 映射为 `{ id, title, type }`，**当前 search 输出不含 `answerCount`**。
- 既有 `answerCount` 来源是 **question metadata API**：`grabber.js:371` `answerCount: info.answer_count ?? null`，来自 `buildQuestionInfoUrl(qid)`（`http.js:75`，`QUESTION_INCLUDE` 含 `answer_count`，`http.js:41`）。每个问题恰 1 次请求（`NETWORK_REQUEST_DELTA = 0`）。

**UPSTREAM_SCHEMA_STATUS（不可从客户端代码断言）：**
- **UNKNOWN / DISCOVERY_REQUIRED**。仅能证明「当前客户端代码消费 `Url`/`Title`/`ContentType` 且未输出 `answerCount`」；**不能**据此推断「官方原始 `zhihu_search` Item schema 不含其他字段（如回答数量）」。官方 API 的真实 Item schema 是当前仓库**未实测**的。
- 因此：**禁止在 T1 discovery 之前声称「官方 Item schema 已证明没有 answerCount」**。决策 A 的第一优先（采用官方字段）是否成立，取决于 T1 真实 schema discovery 的结果。

### §3.2 产品决策

1. **先真实调查，不猜测。** 在 CODE 之前，必须先对官方 `zhihu_search` API 的 **真实 Item schema** 做实测 discovery（见 §15-A），确认是否存在可直接使用的回答数量字段（或其等价物）。
2. **字段优先级：**
   - **第一优先**：若官方 search API Item 直接携带回答数量（或其稳定可推导等价物），则优先采用，**不**额外发起请求。
   - **第二优先**：若官方 search 不携带，则评估用 question-info `answer_count` 补充。**但若该补充需要新增 Cookie 依赖、或对每个搜索结果发起额外请求（扩大请求面），必须先形成明确的产品决策**（是否接受成本 / 隐私 / 请求面扩大），不得默认静默引入。
3. **数据完整性铁律：** `answerCount` 必须来自**可信上游**；缺失或为 `null` 时**优于虚构**（输出 `null` / 省略，绝不编造数字）。
4. **search 整体健壮性：** 单个候选的 `answerCount` 获取失败**不得**导致整个 `search` 命令失败；失败项以 `null` / 缺省呈现，其余候选正常返回（符合 V2 §20.2 enrichment 仅 warning、不破坏 core 的原则）。
5. **JSON 兼容性：** search 输出的 `candidates[]` 新增 `answerCount` 为 **additive optional** 字段；老 reader 忽略即兼容（继承 V2 §18 additive-only）。

### §3.3 待 CODE 阶段解决的问题（非本 DOCUMENT 任务解决）

- 官方 search schema 是否真有回答数量字段（§15-A，**T1 discovery 前不得声称已证明无**）。
- 若需 question-info 补充：是否引入新 Cookie / 多次请求 → 产品决策（见 §16 OPEN-D1）。

## §5 决策 C：Agent analysis projection + capability isolation（Phase 5C 纳入当前阶段）

**标识：** 继承 V2 §9 / §9.1 / §9.2（Phase 5B 已收口）+ 执行 PHASE5_IMPLEMENTATION_AUDIT + PHASE5C_CAPABILITY_ISOLATION_FEASIBILITY

### §5.1 立场（继承既有合同）

- V0.3 **不重新设计** Agent projection，而是**明确继承** V2 已批准合同：
  - **§9 Agent projection contract**：投影在 corpus chunk / map 阶段由**确定性代码**生成，不做永久新文件。
  - **§9.1 capability contract（BLOCKER-4）**：LLM 自身 `NETWORK / SHELL-EXEC / PACKAGE / FILESYSTEM-READ / FILESYSTEM-WRITE / TOOLS` 全 `DENY`；trusted deterministic controller 唯一持有 IO；隔离不可用 → digest / map **fail closed**（`capability_isolation_unavailable`），**禁止**默认降级为 prompt-level mitigation 后继续。
  - **§9.2 Agent projection contract closure（Phase 5B）**：Question / Comments / Full-coverage / Answer body / Assets / Format / Determinism / Failure / Capability 各子合同继续有效。

### §5.2 本阶段必须执行的审计与可行性检查（Phase 5C 纳入 V0.3）

- **V0.3 当前就推进 Agent projection + capability isolation**（用户明确）。V2 §9.2.9 规定 Phase 5B 收口后的下一步是 **Phase 5C — Capability Isolation Feasibility Check**；该检查**由 V0.3 在当前阶段真实执行**，而非「只消费既有结论」——因为当前仓库**不存在**已完成的 `CAPABILITY_ISOLATION_AVAILABLE: YES/NO` 结论可供消费。
- **两项必做工作**：
  1. **PHASE5_IMPLEMENTATION_AUDIT**（实现审计）：核验当前 corpus 管线在哪里把 chunk / projection 交给模型；runtime 是否能够创建 tool-less LLM consumer；controller 与 LLM 的边界。
  2. **PHASE5C_CAPABILITY_ISOLATION_FEASIBILITY**（可行性检查）：核验 NETWORK / SHELL / FS / TOOLS 是否能**确定性 DENY**；如何**证明**（而非只靠 prompt 声明）隔离成立；无法证明时如何 **fail closed**。
- **至少核验 6 项（来自 V2 §9.1 / §9.2.9）：**
  1. 当前 corpus 在哪里把 chunk / projection 交给模型；
  2. runtime 是否能够创建 tool-less LLM consumer；
  3. controller 与 LLM 的边界；
  4. NETWORK / SHELL / FS / TOOLS 是否能确定性 DENY；
  5. 如何**证明**而不是只靠 prompt；
  6. 无法证明时如何 fail closed。
- **门控结果（CODE 阶段门槛）：**
  - **按 target runtime 独立门控（R2-4，删除 PARTIAL 歧义）：** `CAPABILITY_ISOLATION_AVAILABLE[target_runtime] = YES`（该 runtime 有确定性证据）→ **仅允许该 runtime** 进入 Agent projection / isolation 的 CODE（T6）。
  - `= NO` / `UNKNOWN` → `capability_isolation_unavailable` → **该 runtime** 的 digest / map **STOP**（fail closed），不进入相关 CODE。
  - **禁止**「一个 runtime 可用 → 推导其他 runtime 也可用」；每个目标 runtime 独立产出 YES/NO。
- **禁止预设 YES**：在 PHASE5_IMPLEMENTATION_AUDIT / PHASE5C 未产出真实证据前，**不得**假设隔离可用；任何「隔离已具备」的声明都必须有确定性证据（如 runtime 配置 / 拦截测试），不得仅凭 prompt-level 声明。

## §6 决策 D：countMismatch 降级（字段层级修正）

**标识：** `COUNT_MISMATCH_SEVERITY = DIAGNOSTIC_ONLY`

### §6.1 当前事实（已核对 master `e67d3ca`）

- `zhihu-answer-grabber/src/verifier.js` 的 `verifyOutput()`（lines 145–156）：当 `reportedAnswerCount !== answers.length` 时，既设 `result.countMismatch = true`，**又** `result.warnings.push(...)` 把该提示写入 `warnings[]`。
- 这些字段（`result.reportedAnswerCount` / `result.capturedAnswerCount` / `result.countMismatch`）属于 **VERIFIER_DIAGNOSTIC_RESULT**（验证产物），**不是** canonical `answers.json` 的字段。canonical `answers.json` 的对应事实是 `answerCount`（抓取时记录的目标回答数）。
- 这与 V2 §20（enrichment 仅 warning 不破坏 core）及 `references/verification.md`「仅提示，不设失败门」的语义一致为「提示」，但**混入 `warnings[]`** 使其被下游当作失败 / 警告信号消费，造成语义污染。

### §6.2 产品决策

1. `countMismatch` 的严重程度降为 **`DIAGNOSTIC_ONLY`**。
2. **不再进入 `warnings[]`**：CODE 阶段从 `verifier.js` 移除 `result.warnings.push(...)` 那一行（§12.4 行 155），仅保留结构化事实。
3. **不影响 `valid`**：`countMismatch` 历来不设失败门，本决策重申——它永远不改变 `result.valid`。
4. **字段层级明确区分（R9）：**
   - **CANONICAL_CAPTURE_FACT**：canonical `answers.json` 的 `answerCount`（抓取时记录的目标回答数），原事实保持不变。
   - **VERIFIER_DIAGNOSTIC_RESULT**：`verifier` 产物的 `reportedAnswerCount` / `capturedAnswerCount` / `countMismatch` 三字段，继续存在于验证产物中，供调用方按需读取（diagnostic / telemetry / 用户可见提示，但不进入 `warnings` 失败信号通道）。
5. **兼容性：** `verifier` 诊断三字段语义不变；canonical `answers.json` 的 `answerCount` 不变；`verify-output` 既有 14 项校验的权威不变（V2 §26、§18.2）。
6. **对 `handoff.warnings` 的传播效果（R2-5）：** 当前 `make-handoff` 的 `warnings = verification.warnings`（handoff 投影 verifier warnings）。因此 T3 后 `countMismatch` 不再进入 `verifier.warnings` → **也自然不再进入 `handoff.warnings`**。明确：
   - `handoff` schema 不变；
   - `handoff.warnings` 仍投影 `verifier` warnings；

## §7 大型语料四层能力（成本优化）

目标：在**不削弱** V2 既定 coverage / evidence gate 的前提下，为不同规模与不同分析目的提供分层能力。四层定义如下。

### §7.1 层 1：popular-sample（保留现有）

- 实现：`corpus-anthology/scripts/popular-sample.mjs`。
- 行为：按 `voteupCount` 取每题 Top N（默认 6），截断（默认 `max-chars` 1300），**明确标注「不代表整个语料」**（脚本头部与输出头部均有声明）。
- V0.3 立场：**保留现状，不改动**。它是高赞快速预览，不是摘要，不进入 coverage gate。

### §7.2 层 2：top-percent-digest（**新增**产品能力，合同待 §16 OPEN 决策；与 V2 §9.2.3 full-coverage digest 合同存在潜在冲突，见 OPEN-D6 / R2-1）

- **定位**：介于「仅看高赞」与「全量摘要」之间——按 canonical `voteupCount` **降序**取前 **X%** 的回答，使用**完整正文**（非截断）生成 digest。
- **必须输出覆盖比例**：产物须显式声明「本 digest 覆盖语料的前 X%（按 voteupCount 降序），**不代表 100% 语料**」，不得冒充全量。
- **X% 与全部 selection 合同为 OPEN 决策**：百分比取整 / 最低选中数 / 允许范围 / 同赞边界 / tie-break / X=100 路由 / 是否默认 X，均见 §16 OPEN-D2（D2.1–D2.8），**不得私自 APPROVE**。
- **正文完整性**：与 popular-sample 不同，本层用完整正文（不截断），以保留语义与可被 evidence 引用。
- **覆盖披露不变量（APPROVED INVARIANT，R3-4）：** sampled analysis **必须**明确披露——① 它不是全量；② 实际选了多少回答；③ 实际覆盖整个 corpus 的比例 / 范围；④ selection rule。这是已批准硬要求，不随 OPEN 决策改变。
- **具体输出字段（PROPOSED / OPEN，R3-4）：** 建议 `totalAnswers` / `selectedAnswers` / `requestedPercent` / `actualCoveragePercent` / `selectionRule`（§16 OPEN-D2.8），**具体字段名 / 结构仍 `DECISION_STATUS: OPEN`**，由 T7 最终批准；**不得**在 T7 前把具体字段名（如 `actualCoveragePercent`）写成已批准的必输出字段。
- **gate 约束**：本层仍须保留 source-level 可追溯（evidenceSourceIds / sourceCoverage 思路），但允许与全量 digest 不同的聚合粒度；**不得**因此削弱「每个被纳入的 source 都有结构化处理痕迹」这一核心不变量（参照 V2 `verify.mjs` 的 `sourceCoverage` 全覆盖要求的精神，按本层覆盖范围调整，而非取消）。**锁死 `SAMPLED_ANALYSIS != FULL_COVERAGE_DIGEST`**：本层 sampled output **不得**声明为 `task=digest` / full coverage，不得冒充全量 digest（见 OPEN-D6 / R2-1）。

### §7.3 层 3：hierarchical full digest（保留并降本，含 evidence lineage 不变量）

- **定位**：100% 覆盖的全量 digest，是 V2 既定 digest 管线（`chunk.mjs → map → verify.mjs → reduce.mjs`）。
- **降本手段**：引入**中间聚合层**（hierarchical aggregation）——在 chunk-level map 之上先做 sub-topic / sub-cluster 聚合，再向上归并，降低顶层 reduce 的输入规模与 token 成本。
- **不可削弱的 gate**（来自 V2 `verify.mjs` / `reduce.mjs`，CODE 阶段必须保持）：
  - 覆盖率门：`missingSources=0` / `duplicateAssignments=0` / `failedChunks=0` / `invalidEvidenceRefs=0` / `missingMapResults=0` / `staleHashes=0` / `staleMaps=0` / `crossChunkEvidence=0` / `malformedMaps=0` / `duplicateMaps=0` / `missingMappedSources=0`。
  - 逐来源覆盖：`sourceCoverage` 集合必须等于 chunk.sourceIds（全覆盖）；每条必须有非空 `summary`（disposition 不能替代语义覆盖）。
  - 完整性快照：`manifestHash` / `mapSetHash`；`reduce.mjs` 启动时重校，不信任旧 coverage、不重读全部原文。
  - 跨 chunk 证据：`claim.evidenceSourceIds ⊆ 当前 chunk.sourceIds`，`crossChunkEvidence=0`。
- **R10 evidence lineage 不变量（写死，不可削弱）：** 任何 intermediate synthesis / grouped summary **不得切断最终 claim 到原始 answer / source ID 的证据链**。至少要求：
  - 中间 claim 保留合法 `evidenceSourceIds`，或确定性的原始 `source-id` lineage；
  - 上层聚合**只能引用已验证的下层结构**；
  - 最终 claim 必须仍能追溯到 canonical source IDs；
  - **不允许**只引用「summary-3」这类失去原始身份的中间节点；
  - intermediate validation 的具体结构可留 T9 OPEN，但 **lineage invariant 必须在本 Spec 写死**。
- **V0.3 立场**：层 3 的核心 gate 与 evidence lineage 不变量 **一律保留**；中间聚合层只允许在「不削弱上述 gate 与 lineage」的前提下降本。**任何降本方案若导致 coverage / evidence gate / lineage 弱化，均判为违反本 Spec。**

### §7.4 层 4：archive（保持现状）

- 机械拼接、零改写的归档能力（corpus-anthology 既有 archive 模式）。V0.3 **保持现状，不改动**。

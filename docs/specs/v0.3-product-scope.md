## §1 任务背景与动机

`zhihu-grabber-toolkit` 的 V2 rich-content-fidelity 已实现并合并了 Phase 1–4（Rich Content / Question metadata / Comments），并确立了严格的三层内容模型与 Agent 安全隔离合同。当前待推进的边界（V2 §25 Open questions、Phase 5 Agent projection / Capability Isolation）与若干产品层面的清晰度缺口，构成 V0.3 的动机：

1. **搜索规模不可见**：`search` 命令当前只返回问题 ID / 标题 / 类型（见 §12.1），用户在选择抓取目标时不知道该问题有多少回答，无法预估语料规模与成本。
2. **视频能力的产品立场缺失**：V2 §16 将视频定位为「detect + metadata，待真实样本」，但从未给出一个明确的、可被实现遵循的**永久性产品立场**。本 Spec 将其收敛为「永久不支持」，消除 spec-driven 歧义。
3. **Agent projection 的合同归属**：V2 §9/§9.1/§9.2 已定义 Agent 投影与能力隔离合同，但 Phase 5 部分尚在 CODE gate 之前。V0.3 明确「V0.3 阶段只继承该合同，不重新设计、不削弱、不提前解锁 Phase 5C 可行性未验证的能力」。
4. **countMismatch 的语义污染**：当前 `verifier.js` 把 `countMismatch` 同时写入 `warnings[]`（§12.4），使其被当作「失败/警告」信号，但实际语义只是诊断性提示（V2 §20 与 references/verification.md 明确「仅提示，不设失败门」）。需要把该事实从 `warnings[]` 中剥离。
5. **大型语料的 token / 成本压力**：corpus-anthology 已有 `popular-sample`（高赞样本）与 `digest`（100% 覆盖）。但介于「仅看高赞」与「全量摘要」之间的**按覆盖率降序取前 X% 用完整正文**这一常见产品形态缺失；且全量 digest 在超大语料下的成本需要中间聚合层降本，同时**不得削弱既有 coverage / evidence gate**。

## §3 决策 A：搜索结果返回回答数量

**标识：** `SEARCH_ANSWER_COUNT_DISCOVERY_REQUIRED = YES`

### §3.1 当前事实（已核对 master `e67d3ca`）

- 官方搜索客户端 `zhihu-answer-grabber/src/official.js` 的 `searchQuestions()` 返回 `parsed.Data?.Items`，Item 字段为 `Url` / `Title` / `ContentType`（经 `extractQuestionId(item)` 从 `item.Url` 提取 qid）。**官方 search API 的 Item schema 不含 `answerCount` 字段。**
- `zhihu-answer-grabber/src/cli.js` 的 `cmdSearch()`（lines 221–256）将 Item 映射为 `{ id, title, type }`，**search 输出不含 `answerCount`**。
- 既有 `answerCount` 来源是 **question metadata API**：`grabber.js:371` `answerCount: info.answer_count ?? null`，来自 `buildQuestionInfoUrl(qid)`（`http.js:75`，`QUESTION_INCLUDE` 含 `answer_count`，`http.js:41`）。每个问题恰 1 次请求（`NETWORK_REQUEST_DELTA = 0`）。

### §3.2 产品决策

1. **先真实调查，不猜测。** 在 CODE 之前，必须先对官方 `zhihu_search` API 的 **真实 Item schema** 做实测 discovery（见 §15-A），确认是否存在可直接使用的回答数量字段（或其等价物）。
2. **字段优先级：**
   - **第一优先**：若官方 search API Item 直接携带回答数量（或其稳定可推导等价物），则优先采用，**不**额外发起请求。
   - **第二优先**：若官方 search 不携带，则评估用 question-info `answer_count` 补充。**但若该补充需要新增 Cookie 依赖、或对每个搜索结果发起额外请求（扩大请求面），必须先形成明确的产品决策**（是否接受成本 / 隐私 / 请求面扩大），不得默认静默引入。
3. **数据完整性铁律：** `answerCount` 必须来自**可信上游**；缺失或为 `null` 时**优于虚构**（输出 `null` / 省略，绝不编造数字）。
4. **search 整体健壮性：** 单个候选的 `answerCount` 获取失败**不得**导致整个 `search` 命令失败；失败项以 `null` / 缺省呈现，其余候选正常返回（符合 V2 §20.2 enrichment 仅 warning、不破坏 core 的原则）。
5. **JSON 兼容性：** search 输出的 `candidates[]` 新增 `answerCount` 为 **additive optional** 字段；老 reader 忽略即兼容（继承 V2 §18 additive-only）。

### §3.3 待 CODE 阶段解决的问题（非本 DOCUMENT 任务解决）

- 官方 search schema 是否真有回答数量字段（§15-A）。
- 若需 question-info 补充：是否引入新 Cookie / 多次请求 → 产品决策（见 §16 Open Decisions）。

## §5 决策 C：Agent analysis projection

**标识：** 继承 V2 §9 / §9.1 / §9.2（Phase 5B 已收口）

### §5.1 立场

- V0.3 **不重新设计** Agent projection，而是**明确继承** V2 已批准合同：
  - **§9 Agent projection contract**：投影在 corpus chunk / map 阶段由**确定性代码**生成，不做永久新文件。
  - **§9.1 capability contract（BLOCKER-4）**：LLM 自身 `NETWORK / SHELL-EXEC / PACKAGE / FILESYSTEM-READ / FILESYSTEM-WRITE / TOOLS` 全 `DENY`；trusted deterministic controller 唯一持有 IO；隔离不可用 → digest / map **fail closed**（`capability_isolation_unavailable`），**禁止**默认降级为 prompt-level mitigation 后继续。
  - **§9.2 Agent projection contract closure（Phase 5B）**：Question / Comments / Full-coverage / Answer body / Assets / Format / Determinism / Failure / Capability 各子合同继续有效。

### §5.2 约束

- **不新增永久 canonical 正文文件**：Agent 投影是 corpus chunk / map 阶段的确定性派生产物，不得向 `answers.json` canonical 形态写入新的永久正文文件（遵守 V2 §9 与 §18 additive-only）。
- **Phase 5C 不解锁**：V2 §9.2.9 规定，Phase 5B 仅为合同收口，下一步是独立的 **Phase 5C — Capability Isolation Feasibility Check**（验证宿主 / runtime 能否实例化 tool-less LLM consumer）。V0.3 **不**声称当前实现已提供该隔离，也**不**提前解锁 Phase 5C 仍在验证中的能力。若 Phase 5C 判定 `CAPABILITY_ISOLATION_AVAILABLE: NO`，仍须 `capability_isolation_unavailable` → STOP。
- **CODE 阶段对 C 的工作内容**：确认投影生成点（corpus chunk 阶段确定性脚本）、验证其不新增永久 canonical 正文文件、回归 V2 §26 Acceptance 中 Agent projection 对抗项。**不**在本 Spec 引入新的 projection 设计。

## §6 决策 D：countMismatch 降级

**标识：** `COUNT_MISMATCH_SEVERITY = DIAGNOSTIC_ONLY`

### §6.1 当前事实（已核对 master `e67d3ca`）

- `zhihu-answer-grabber/src/verifier.js` 的 `verifyOutput()`（lines 145–156）：当 `reportedAnswerCount !== answers.length` 时，既设 `result.countMismatch = true`，**又** `result.warnings.push(...)` 把该提示写入 `warnings[]`。
- 这与 V2 §20（enrichment 仅 warning 不破坏 core）及 `references/verification.md`「仅提示，不设失败门」的语义一致为「提示」，但**混入 `warnings[]`** 使其被下游当作失败 / 警告信号消费，造成语义污染。

### §6.2 产品决策

1. `countMismatch` 的严重程度降为 **`DIAGNOSTIC_ONLY`**。
2. **不再进入 `warnings[]`**：CODE 阶段从 `verifier.js` 移除 `result.warnings.push(...)` 那一行（§12.4 行 155），仅保留结构化事实。
3. **不影响 `valid`**：`countMismatch` 历来不设失败门，本决策重申——它永远不改变 `result.valid`。
4. **保留结构化事实**：`result.reportedAnswerCount` / `result.capturedAnswerCount` / `result.countMismatch` 三个字段继续存在于验证产物中，供调用方按需读取（diagnostic / telemetry / 用户可见提示，但不进入 `warnings` 失败信号通道）。
5. **兼容性：** `answers.json` 的 `reportedAnswerCount` 等字段语义不变；`verify-output` 既有 14 项校验的权威不变（V2 §26、§18.2）。

## §7 大型语料四层能力（成本优化）

目标：在**不削弱** V2 既定 coverage / evidence gate 的前提下，为不同规模与不同分析目的提供分层能力。四层定义如下。

### §7.1 层 1：popular-sample（保留现有）

- 实现：`corpus-anthology/scripts/popular-sample.mjs`。
- 行为：按 `voteupCount` 取每题 Top N（默认 6），截断（默认 `max-chars` 1300），**明确标注「不代表整个语料」**（脚本头部与输出头部均有声明）。
- V0.3 立场：**保留现状，不改动**。它是高赞快速预览，不是摘要，不进入 coverage gate。

### §7.2 层 2：top-percent-digest（**新增**产品能力）

- **定位**：介于「仅看高赞」与「全量摘要」之间——按 canonical `voteupCount` **降序**取前 **X%** 的回答，使用**完整正文**（非截断）生成 digest。
- **必须输出覆盖比例**：产物须显式声明「本 digest 覆盖语料的前 X%（按 voteupCount 降序），**不代表 100% 语料**」，不得冒充全量。
- **X% 默认值**：`DECISION_STATUS: OPEN`（见 §16），CODE 前需基于真实 token / 成本测量给出默认值建议。
- **正文完整性**：与 popular-sample 不同，本层用完整正文（不截断），以保留语义与可被 evidence 引用。
- **gate 约束**：本层仍须保留 source-level 可追溯（evidenceSourceIds / sourceCoverage 思路），但允许与全量 digest 不同的聚合粒度；**不得**因此削弱「每个被纳入的 source 都有结构化处理痕迹」这一核心不变量（参照 V2 `verify.mjs` 的 `sourceCoverage` 全覆盖要求的精神，按本层覆盖范围调整，而非取消）。

### §7.3 层 3：hierarchical full digest（保留并降本）

- **定位**：100% 覆盖的全量 digest，是 V2 既定 digest 管线（`chunk.mjs → map → verify.mjs → reduce.mjs`）。
- **降本手段**：引入**中间聚合层**（hierarchical aggregation）——在 chunk-level map 之上先做 sub-topic / sub-cluster 聚合，再向上归并，降低顶层 reduce 的输入规模与 token 成本。
- **不可削弱的 gate**（来自 V2 `verify.mjs` / `reduce.mjs`，CODE 阶段必须保持）：
  - 覆盖率门：`missingSources=0` / `duplicateAssignments=0` / `failedChunks=0` / `invalidEvidenceRefs=0` / `missingMapResults=0` / `staleHashes=0` / `staleMaps=0` / `crossChunkEvidence=0` / `malformedMaps=0` / `duplicateMaps=0` / `missingMappedSources=0`。
  - 逐来源覆盖：`sourceCoverage` 集合必须等于 chunk.sourceIds（全覆盖）；每条必须有非空 `summary`（disposition 不能替代语义覆盖）。
  - 完整性快照：`manifestHash` / `mapSetHash`；`reduce.mjs` 启动时重校，不信任旧 coverage、不重读全部原文。
  - 跨 chunk 证据：`claim.evidenceSourceIds ⊆ 当前 chunk.sourceIds`，`crossChunkEvidence=0`。
- **V0.3 立场**：层 3 的核心 gate **一律保留**；中间聚合层只允许在「不削弱上述 gate」的前提下降本。**任何降本方案若导致 coverage / evidence gate 弱化，均判为违反本 Spec。**

### §7.4 层 4：archive（保持现状）

- 机械拼接、零改写的归档能力（corpus-anthology 既有 archive 模式）。V0.3 **保持现状，不改动**。
